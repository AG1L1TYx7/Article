# Internationalisation

Two separate things, kept separate on purpose:

- **The interface language** — menus, buttons, messages, dates and
  numbers. Follows the reader. English and Nepali today.
- **A story's language** — what an article is written in. Each article
  carries its own `locale`, and a translation is a second article linked
  to the first.

A Nepali reader on a site that mostly publishes in English sees Nepali
chrome around English stories, each marked as English, with a link to a
Nepali version wherever one exists. That is the honest state of affairs
rather than a filtered-down front page.

## How the interface language is chosen

`src/proxy.ts` decides once per request, in this order:

1. the `locale` cookie — set by the switcher in the masthead, footer,
   newsroom sidebar or on the
   account page, kept for a year;
2. the browser's `Accept-Language`, by weight, matching `ne-NP` to `ne`;
3. English.

It passes the answer down as the `x-locale` request header, sets
`Content-Language` on the response, and `src/i18n/server.ts` reads it
back with `getLocale()` / `getI18n()`. Client components get the same
answer from `useI18n()` (`src/i18n/client.tsx`), fed by the root layout
with that one language's dictionary, so both sides of hydration render
the same text.

No URL prefixes (`/ne/...`). They are the right choice when the *content*
is per language and you want two indexable front pages; here the content
is mixed and the language is a reader preference, so a cookie is the
correct tool and every existing link keeps working.

## Using it

Server components:

```tsx
import { getI18n } from "@/i18n/server";

const { t, n, formatDate } = await getI18n();
t("home.moreStories");                       // "More stories"
t("article.moreFrom", { section: "Sport" }); // "More from Sport"
n(3, "common.articles");                     // "3 articles" / "3 artículos"
formatDate(article.publishedAt);             // "20 Sept 2026" / "20 sept 2026"
```

Client components: `const { t, n, formatDate } = useI18n();` — same API.

Keys are checked at compile time (`MessageKey` in `src/i18n/t.ts`), so a
typo is a type error, not a blank label. Placeholders are `{name}`;
plurals are `.one` / `.other` pairs chosen with `Intl.PluralRules` and
given `{count}` in the locale's digits.

Every formatter pins UTC, like `lib/format.ts` always has, so the server
and the reader's browser print identical strings and React never reports
a hydration mismatch on a date.

## Adding a language

1. Add its code to `LOCALES` in `src/i18n/config.ts`, with its own name
   in `LOCALE_NAMES`, its BCP 47 tag in `INTL_LOCALE`, its direction in
   `LOCALE_DIR` and its Open Graph code in `OG_LOCALE`.
2. Copy `src/i18n/messages/en.ts` to `messages/<code>.ts`, type it as
   `Messages`, and translate every value. The type checker refuses a
   missing or extra key; `tests/unit/i18n.test.ts` additionally refuses a
   changed placeholder and a value left identical to English.
3. Register it in `src/i18n/messages/index.ts`.

Nothing else lists locales. The switcher, the editor's Language field,
the article page's "Read this in …" links and the sitemap all read the
config.

## Stories in more than one language

In the editor, **Language** is the language the story is written in and
**Translation of** is the slug of the article it translates. Saving a
translation:

- marks its headline, dek and body with `lang="ne"` so screen readers
  switch voice and hyphenation follows the text;
- adds "Read this story in: English / Español" links on both pages;
- emits `hreflang` alternates in both pages' `<head>` and in the sitemap,
  so search engines show a reader the version in their language rather
  than treating the two as duplicates;
- shows a small language tag on the story's card in any list where it
  differs from the reader's interface language.

Two translations of one original reach each other through the original;
a translation of a translation is not supported, and there is no reason
to want one.

## What is deliberately not translated

- **The privacy policy and terms.** A translated policy is a legal
  document in its own right and needs a lawyer. Both pages show a notice,
  in the reader's language, that they are available in English only.
- **The newsroom's inner pages** (editor, moderation queue, analytics,
  people, audit log, settings). The sidebar and shared chrome are
  translated; the deep forms are English. They are used by staff, and
  translating a few hundred editorial strings would delay the reader-
  facing work that matters more. Add keys under `dashboard.*` when it is
  wanted; the mechanism is the same.
- **Brand and service names** (X, Facebook, WhatsApp, RSS, JSON) and the
  account-deletion confirmation phrase, which stays `delete my account`
  in every language so it can be documented once.
- **Slugs, handles and category names.** Those are data, entered by
  staff; a Nepali section can simply be named in Nepali.

## Testing

- `tests/unit/i18n.test.ts` — negotiation, key parity between languages,
  placeholder parity, plurals, Nepali formatting (Devanagari digits and
  lakh grouping), relative times.
- `tests/e2e/i18n.spec.ts` — default English with `Content-Language`,
  Nepali from `Accept-Language`, the switcher (with JavaScript off, since
  it is a plain form), cookie persistence, a translated pair linking both
  ways with `hreflang`, the sitemap alternates, and the legal-page notice.
